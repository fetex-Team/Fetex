# 04. 예측 기반 재배치 (`taxi_strategy = "forecast"`)

파일: `module4_dispatch/forecast_repositioner.py`, `measure_wait_time.py` / 테스트: `tests/test_forecast_repositioner.py`

---

## 문제

| 관찰 | 설명 |
|---|---|
| 과제 핵심은 "수요 예측 → 배차" | 그런데 위치별(H3 칸) 수요 예측 모델 `demand_v2`를 직접 쓰는 배차 전략이 없었다 |
| RL은 예측을 간접적으로만 사용 | 구역(카테고리) 단위 예측을 입력으로 받지만, 어디로 보낼지는 학습한 정책이 정함 |
| 기존 `forecast_dispatcher.py` | 연결이 끊겨 있었고, 모든 택시를 칸 안의 첫 번째 도로 하나로 보내는 문제가 있었음 |

## 결정

빈 택시는 평소 순찰처럼 움직이고, **5분마다** 아래를 한다.

| 단계 | 방법 | 근거 |
|---|---|---|
| ① 예측 | `demand_v2`로 칸별 다음 30분(10분 × 3칸) 호출 수 λ_c 예측 | 학습과 같은 피처: 지난 7일(학습 로그와 같은 생성기·시드) + 오늘 지금까지 실제 호출 + 실측 날씨. **미래 호출은 보지 않음** |
| ② 목표 배치 | 빈 택시 N대를 **λ_c^(2/3)** 비율로 칸에 나눔 | 손님이 무작위로 나타날 때 가장 가까운 빈 택시까지 평균 거리는 그 칸 택시 밀도의 −1/2제곱에 비례 → Σ λ_c · n_c^(−1/2)를 최소화하는 배치가 n_c ∝ λ_c^(2/3). 정비례로 몰면 한산한 칸이 비어 손해 |
| ③ 이동 대상 | 목표보다 많은 칸(남는 칸)의 빈 택시 → 모자란 칸 | 남는 만큼만 옮김 |
| ④ 도착 도로 | 그 칸에서 지난 8일 호출이 많았던 도로를 호출 비율대로, 서로 다른 도로로 흩어 고름 | 한 도로에 몰리면 오히려 칸 안 거리가 늘어남 |
| ⑤ 누구를 어디로 | 다익스트라 도로 이동시간 비용의 헝가리안 매칭 | 배차와 같은 비용 기준 |
| ⑥ 제한 | 이동 3분 이하, 한 번에 빈 택시의 30%까지 | 멀리 옮기는 동안 생기는 손해 제한 |
| ⑦ **안전장치** | **빈 택시가 전체의 30% 미만이면 재배치하지 않음** | 아래 v1 결과 참고 |

이동 중인 택시도 빈 택시라 그 사이 호출이 오면 그대로 배차된다(배차가 우선).

## v1 (안전장치 없음) → 결함 발견

| 조건 (7일) | 순찰 | 예측 재배치 v1 |
|---|---:|---:|
| 카카오 몫: 놓친 손님/일 | 22.9 | 23.7 |
| 카카오 몫: 평균 대기 | 60.1초 | 59.7초 |
| 손님 100%: 놓친 손님/일 | **266.3** | 336.0 |

손님 100%의 가장 바쁜 날(9/10)에 놓친 손님 973 → 1,392명. 택시가 부족할 때 옮기면 그 사이 근처 호출을 놓쳐 손해였다.

## 안전장치 기준 정하기 (검증 날짜 — 평가 7일 아님)

9/8(화), 9/17(목), 손님 100%. 빈 택시 비율 기준별 놓친 손님:

| 기준 | 9/8 | 9/17 | 합계 |
|---|---:|---:|---:|
| 순찰 | 631 | 980 | 1,611 |
| 0 (안전장치 없음) | 623 | 968 | 1,591 |
| 0.2 | 680 | 968 | 1,648 |
| **0.3** | **588** | 980 | **1,568** |
| 0.4 | 618 | 980 | 1,598 |

→ **0.3** 선택 (`forecast_min_idle_ratio`). 9/17처럼 빈 택시가 거의 없는 날은 재배치를 전혀 하지 않아 순찰과 결과가 숫자까지 같다(안전장치가 정확히 동작한다는 확인이기도 함). 원자료: `results/repeat/tune_*`

## v2 (안전장치) 최종 결과 — 평가 7일

| 전략 | 평균 대기 (카카오 몫) | 놓친 손님/일 (카카오 몫) | 놓친 손님/일 (손님 100%) | 평균 대기 (손님 100%) |
|---|---:|---:|---:|---:|
| 순찰 | 60.1초 | 22.9 | **266.3** | 108.8초 |
| **예측 재배치 v2** | **59.4초** | **17.4** | 293.7 | 108.8초 |
| 시간표 선배치 | 69.6초 | 34.3 | 315.3 | 115.7초 |
| RL | 75.5초 | 25.7 | 329.7 | 119.7초 |

| 순찰 대비 예측 재배치 v2 | 차이 (95% 신뢰구간) | 더 나은 날 | 판단 |
|---|---|---|---|
| 카카오 몫 놓친 손님 | −5.4명 (−13.6 ~ +2.7) | 5/7 | 줄어드는 경향, 확실하지 않음 (p=0.45) |
| 카카오 몫 평균 대기 | −0.7초 (−2.5 ~ +1.0) | 4/7 | 차이 없음 |
| 손님 100% 놓친 손님 | +27.4명 (−35.0 ~ +89.8) | 3/7 | 차이 없음 (9/10은 순찰과 동일) |

**결론**
- 미리 옮기는 전략 중 가장 좋다: 시간표 선배치보다 10초, RL보다 16초 짧다 (7일 모두).
- 순찰과는 통계적으로 구분되지 않는다. 평소(카카오 몫)엔 놓친 손님이 줄어드는 경향, 바쁠 땐 비슷.
- 손님 100%에서 빈 택시가 10~30%인 날(9/18, 10/13)은 몇십 대만 옮겨도 결과가 크게 흔들린다(혼잡 상태의 연쇄 효과).

## 검증

- `tests/test_forecast_repositioner.py`: λ^(2/3) 배분 합·비율, **미래 호출 미사용**, 도착 도로 분산
- 예측 모델이 시뮬레이션 날짜 이후 데이터로 학습됐으면 실행을 거부 (누수 방지)
- `tools/check_determinism.py --strategy forecast`: 두 번 실행 결과 동일

## 한계·후속

- 이동 판단이 "칸 단위 대수"라 같은 칸 안의 위치 차이는 보지 않음
- 택시 부족 기준(30%)은 검증 날짜 2일로 정한 값. 날짜를 늘리면 더 안정적으로 정할 수 있음
- 신호·정체를 반영한 도로 시간(남은 작업 2번)이 들어가면 이동 비용이 더 정확해짐

## 설정

| 키 | 기본 | 의미 |
|---|---|---|
| `taxi_strategy` | — | `forecast`로 선택 |
| `forecast_tick_sec` | 300 | 재배치 주기 |
| `forecast_horizon_buckets` | 3 | 예측 구간 (10분 칸 수, 3 = 30분) |
| `forecast_alloc_power` | 0.6667 | 목표 = 예측^이 값 비율 |
| `forecast_max_move_sec` | 180 | 한 번 이동 최대 시간 |
| `reposition_fraction` | 0.3 | 한 번에 옮길 수 있는 빈 택시 비율 |
| `forecast_min_idle_ratio` | 0.3 | 빈 택시가 이 비율 미만이면 재배치 중단 |
