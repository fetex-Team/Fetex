# 05. RL 재학습

파일: `module4_dispatch/rl_env.py`, `module4_dispatch/rl_train.py`, `module4_dispatch/rl_reposition_model.zip`

---

## 문제

| 관찰 | 설명 |
|---|---|
| 예전 RL 정책은 가정 수요로 학습됨 | 실데이터 수요로 비교하면 학습·평가 분포가 달라 불공정 |
| 학습 날짜를 무작위로 뽑음 | 평가 날짜와 겹칠 수 있음 (답 보고 시험) |
| 예전 "RL 96.0% vs 순찰 94.3%" | 하루·1번 실행이고, 해시 시드 고정 전이라 실행 간 변동이 섞인 결과 |

## 결정

| 항목 | 내용 |
|---|---|
| 학습 수요 | 01장의 실데이터 보정 수요 (2025 통계, 카카오 몫, 실측 날씨) |
| 예측 입력 | 같은 로그로 다시 학습한 구역별 예측 (`train_category_demand.py --logs ...`) |
| 학습 날짜 | `rl_train_start` ~ `rl_train_end` = 2026-07-13 ~ 09-06 (예측 모델 학습 기간과 같고, 평가 날짜와 겹치지 않음) |
| 학습량 | PPO 51,200번 결정 (하루 840번 × 약 61일치), 병렬 환경 4개, 약 3시간 |
| 백업 | 새 정책 저장 전 기존 정책을 `rl_model_backups/`에 자동 백업 |

## 구조 (변경 없음)

| 항목 | 내용 |
|---|---|
| 상태 (19개) | 6개 구역(학교·주거·회사·음식점·지하철·버스)별 대기 손님, 빈 택시, 예측 수요 + 시각 |
| 행동 | 1분마다 구역별 0~3점 → 점수 비율대로 빈 택시 배분 |
| 보상 | 탑승 +3, 타임아웃 −8, 대기 손님 1명당 −0.1, 이동 거리 감점, 시간표 분포 일치 +0.5 |

## 결과 (7일, 다익스트라 배차)

| 조건 | 순찰 | RL | 판단 |
|---|---:|---:|---|
| 카카오 몫 평균 대기 | 60.1초 | 75.5초 | RL이 7일 모두 김 (p=0.016) |
| 손님 100% 놓친 손님/일 | 266.3 | 329.7 | 차이 확실하지 않음 |

## 왜 순찰보다 못한가 (분석)

| 원인 | 근거 |
|---|---|
| 행동 단위가 지도 위치가 아님 | "음식점 구역"은 강남역 곳곳에 흩어진 도로 모음 → 보내도 손님 근처라는 보장이 없음 |
| 옮기는 동안의 손해 | 재생 파일 분석: 배차 후 픽업까지 순찰 77.3초 vs RL 86.4초 (직선 배차 기준) → 대기 증가가 전부 이동 거리에서 나옴 |
| 보상 설계 | 대기 손님 감점(−0.1/분)과 이동 감점이 작고, 시간표 분포 일치(+0.5)가 오히려 대기가 긴 시간표 선배치를 따라 하게 만듦 |
| 직선 거리 배차로 학습 | 다익스트라 배차 환경과 다름 → 이 환경에서 재학습하면 달라질 수 있음 |

## 후속 (팀 분담)

- 행동 공간을 H3 칸 8개로, 보상에 대기시간 가중·이동 패널티 강화, 다익스트라 배차 환경에서 재학습
- 학습 보상 곡선 기록 (현재 Monitor 미적용)
