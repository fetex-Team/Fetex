# 실데이터 기반 수요 보정 (TIMS 500m 격자 + 서울시 시간대 통계)

담당: 이동규 / 코드: `demand_model.py`, `passenger_spawn_manager.py`(실데이터 모드), `scripts/generate_demand_logs.py`,
`tools/fleet_sizing.py` / 데이터: `data/external/` (출처·한계는 `data/external/README.md`)

## 1. 왜 바꿨나
| 문제 | 예전 | 지금 |
|---|---|---|
| 호출 규모·지역 분포의 근거 | "회사 1곳당 100명, 퇴근 시 30% 택시" 같은 가정값 | 국토교통부 TIMS 2025년 500m 격자 실측 승차 건수 |
| 시간대 분포 | 등교·출근·점심·퇴근 이벤트 가정 | 서울시 택시 시간대별 이용 비율(평일/주말 별도) |
| 계절·요일 | 없음 | TIMS 월별 계절성(±7%) + 서울시 요일 배율 |
| 공정 비교 | 승객 생성이 "실제 도착 인원"에 따라 달라짐 + 택시 매니저와 같은 난수 사용 → 전략마다 손님 목록이 달랐음 (재생 파일 지문 `7caab31d…` vs `e2b08fd0…`) | 하루 호출 목록을 시작 전에 시드로 미리 만듦(외생 수요) → 전략이 달라도 지문 동일 |
| 학습 데이터 | 시뮬레이션 1회(약 16분)마다 하루치, 밤 시간 없음 | SUMO 없이 8주(56일)·24시간을 약 10초에 생성, 시뮬레이션 호출과 같은 규칙·시드 |

## 2. 방법
1. **영역 안 하루 호출 수** = Σ(격자 c의 그 달 하루 평균 승차 × 시뮬레이션 영역과 겹치는 면적 비율) × 요일 배율
   - 영역(약 1km × 1km)과 겹치는 TIMS 격자 9개, 연평균 하루 **약 9,880건**.
   - 요일 배율: 월 0.94, 화 1.09, 수 1.06, 목 1.11, 금 1.04, 토 0.95, 일 0.81 (평일 공휴일 = 일요일 배율 + 주말 시간대).
2. **시간대**: 서울시 2022년 1월 택시 시간대별 이용 비율(평일·주말). 시간마다 포아송 과정으로 호출 시각을 뽑는다.
3. **승차 위치**: 격자별 TIMS 비율로 칸을 고르고(강남역 사거리 두 칸이 67%), 칸 안에서는 POI 가중치(지하철 출구 3, 버스정류장 2,
   백화점 11~21시 2.5, 음식점 점심·저녁 2.5, 회사 17~21시 2.5, 주거 6~10시 2)로 도로를 고른다. 도로 위 위치는 10~90% 무작위.
4. **목적지**: TIMS 격자 평균 운행거리 L(강남역 약 10.5km)로부터 1km 안에서 끝나는 손님 비율 = 1 − e^(−1/L) ≈ **9%**만 영역 안에서
   내리고, 나머지는 경계 도로로 나간다(밖으로 가는 손님). 강남구는 서울 하차 1위 지역이라, 밖으로 나간 택시만큼 빈 택시가 다시 들어온다고 본다.
5. **날씨**: 기존 "날씨적용" 기능 유지 — 택시 선택 확률 가산값을 호출량 배율(1 + 가산값)로 적용.
6. **재현성**: 난수는 `random.Random("fetex-demand|시드|날짜")` 전용 스트림. 같은 날짜·시드면 시각·도로까지 완전히 같다.
7. **매출 추정**: 태운 손님 수 × TIMS 실측 평균 요금(영역 격자 가중 평균 약 16,300원) → 결과에 `est_revenue_won`.

`config.json`
```json
"demand_source": "real",          // "synthetic"이면 예전 가정 모델
"real_demand_scale": 1.0,         // 실측량 중 이 시뮬레이션 택시가 맡는 비율
"real_internal_trip_km": 1.0      // 이보다 짧은 운행만 영역 안 하차
```

## 3. 검증
- `python tests/test_demand_model.py` — 좌표 변환(pyproj와 1cm 이내), 격자 코드, 총량·격자 비율·영역 안 하차 비율,
  결정성(전역 난수를 건드려도 같은 결과), 주말 프로파일, POI 가중치 (5개 통과).
- 시뮬레이션 1시간 실행(2026-09-26 토, 9~10시): 예정 호출 401~426건 중 생성 실패 0건.
- 8주 학습 로그(2026-07-13 ~ 09-06): 573,430건, 평일 하루 약 9,000~10,500건 / 주말 약 7,800~9,200건.

## 4. 이 데이터로 다시 학습한 결과
| 항목 | 예전(가정 수요, H3 res 7, 셀 3개, 8일) | 지금(실측 보정, H3 res 8, 셀 8개, 8주) |
|---|---|---|
| demand_v2 (t+1~t+6, 10분) WAPE | 44.6% | **23.0%** |
| RMSE / MAE | 2.91 / 1.91 | 3.22 / 1.99 (셀당 수요가 커져 절대 오차는 비슷) |

H3 해상도 비교(`eda/h3_resolution_compare.py`, 실측 보정 14일, 10분 칸): res 7은 셀 3개에 한 칸이 86%(너무 거칠다),
res 9는 0인 칸 44%·자기상관 0.21, res 10은 0인 칸 60%(너무 잘다) → **res 8**(셀 8개, 0인 칸 27%, 한 칸 최대 46%, 자기상관 0.39).
또한 실측 원천이 500m 격자라 그보다 작은 칸(res 9, 변 201m)의 차이는 실측이 아니라 POI 가정에서 나온다 → 500m급인 res 8이 데이터 해상도와 맞다.

## 5. 한계
- TIMS는 월 합계라 시간대·요일 분포는 서울 전체 비율(2022년 1월)을 쓴다. 강남역 특유의 심야 집중은 덜 반영된다.
- 칸 안의 도로별 배분은 POI 가정이다(실측 아님).
- 영역 밖 이동을 경계 도로 하차로 단순화했다. 택시가 밖에서 보내는 시간(평균 21분)은 "같은 수의 빈 택시가 들어온다"는 가정으로 대신한다.
- 실측량 전체를 시뮬레이션 택시가 맡는다고 가정한다(`real_demand_scale` 1.0). 카카오 T 호출 비중만 보려면 이 값을 낮춘다.
- RL 재배치 정책(`rl_reposition_model.zip`)은 예전 가정 수요로 학습됐다. 정책 입력(카테고리별 수요 예측)은 실측 보정 데이터로 다시 학습했지만,
  정책 자체는 `module4_dispatch/rl_train.py`로 재학습해야 새 수요 분포에 맞춰진다(14시간 에피소드 × 수십 회, 수 시간 소요).
