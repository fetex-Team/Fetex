## 1. 왜 바꿨나
| 문제 | 예전 | 지금 |
|---|---|---|
| 호출 규모·지역 분포의 근거 | "회사 1곳당 100명, 퇴근 시 30% 택시" 같은 가정값 | 국토교통부 TIMS 2025년 500m 격자 실측 승차 건수 |
| 시간대 분포 | 등교·출근·점심·퇴근 이벤트 가정 | 서울시 2025년 택시 시간대별 이용 비율(평일/주말 별도) |
| 계절·요일 | 없음 | TIMS 월별 계절성(±7%) + 강남구 2025 월별 평일/주말 배율 + 요일 배율 |
| 공정 비교 | 승객 생성이 "실제 도착 인원"에 따라 달라짐 + 택시 매니저와 같은 난수 사용 → 전략마다 손님 목록이 달랐음 (재생 파일 지문 `7caab31d…` vs `e2b08fd0…`) | 하루 호출 목록을 시작 전에 시드로 미리 만듦(외생 수요) → 전략이 달라도 지문 동일 |
| 학습 데이터 | 시뮬레이션 1회(약 16분)마다 하루치, 밤 시간 없음 | SUMO 없이 8주(56일)·24시간을 약 10초에 생성, 시뮬레이션 호출과 같은 규칙·시드 |

## 2. 방법
1. **영역 안 하루 호출 수** = Σ(격자 c의 그 달 하루 평균 승차 × 시뮬레이션 영역과 겹치는 면적 비율) × 강남구 그 달 평일(또는 주말) 배율 × 요일 배율
   - 영역(약 1km × 1km)과 겹치는 TIMS 격자 9개, 연평균 하루 **약 9,880건**.
   - 강남구 배율(2025): 평일 0.93~1.06, 주말 0.82~0.90 (월별, `gangnam_taxi_pickups_2025.csv`).
   - 요일 배율(2022년 1월, 평일 5일 안·주말 2일 안에서 평균 1이 되게 다시 나눔). 평일 공휴일 = 일요일 배율 + 주말 시간대.
   - 그중 카카오 T 몫 `real_demand_scale` = **0.77** (앱 호출 80% × 카카오 점유율 96%, 출처 `data/external/README.md`).
2. **시간대**: 서울시 2025년 택시 시간대별 이용 비율(평일·주말). 시간마다 포아송 과정으로 호출 시각을 뽑는다.
   2022년 1월(영업 제한 시기)보다 9~23시 비중이 낮다: 평일 72.9% → 66.7%, 주말 60.3%.
3. **승차 위치**: 격자별 TIMS 비율로 칸을 고르고(강남역 사거리 두 칸이 67%), 칸 안에서는 POI 가중치(지하철 출구 3, 버스정류장 2,
   백화점 11~21시 2.5, 음식점 점심·저녁 2.5, 회사 17~21시 2.5, 주거 6~10시 2)로 도로를 고른다. 도로 위 위치는 10~90% 무작위.
4. **목적지**: TIMS 격자 평균 운행거리 L(강남역 약 10.5km)로부터 1km 안에서 끝나는 손님 비율 = 1 − e^(−1/L) ≈ **9%**만 영역 안에서
   내리고, 나머지는 경계 도로로 나간다(밖으로 가는 손님). 강남구는 서울 하차 1위 지역이라, 밖으로 나간 택시만큼 빈 택시가 다시 들어온다고 본다.
5. **날씨**: 그날의 **실측 시간별 강수**(Open-Meteo 과거 자료, `module1_simulation/weather_history.py`)로 시간마다 `1 + 0.0199 × 강수mm`(최대 30mm)배.
   그날 파일이 없을 때만 예전 "날씨적용"(실행 시점 실시간 날씨 가산값)으로 대체. 결과에 `weather_source`, `precip_mm_in_window`.
6. **재현성**: 난수는 `random.Random("fetex-demand|시드|날짜")` 전용 스트림. 같은 날짜·시드면 시각·도로까지 완전히 같다.
   시뮬레이션 전체도 파이썬 해시 시드를 0으로 고정(`module1_simulation/reproducibility.py`)해 같은 설정이면 결과가 숫자까지 같다
   (`module4_dispatch/experiments/check_determinism.py`: 고정 시 두 번 실행 결과 동일, 고정 해제 시 다름을 확인).
7. **매출 추정**: 태운 손님 수 × TIMS 실측 평균 요금(영역 격자 가중 평균 약 16,300원) → 결과에 `est_revenue_won`.

`config.json`
```json
"demand_source": "real",          // "synthetic"이면 예전 가정 모델
"real_demand_scale": 0.77,        // 실측량 중 카카오 T 몫
"real_internal_trip_km": 1.0,     // 이보다 짧은 운행만 영역 안 하차
"use_historical_weather": true,   // 실측 날씨 파일 사용
"taxi_external_away": false       // true: 밖으로 나간 택시가 늦게 돌아오는 민감도 시나리오
```

## 3. 검증
- `python tests/test_demand_model.py` — 좌표 변환(pyproj와 1cm 이내), 격자 코드, 총량·격자 비율·영역 안 하차 비율,
  결정성(전역 난수를 건드려도 같은 결과), 주말·평일 배율, 시간별 강수 배율, POI 가중치 (6개 통과).
- `python tests/test_weather_history.py` — 실측 날씨 24시간 읽기, 합성 파일 제외, 빠진 날 처리 (2개 통과).
- 8주 학습 로그(2026-07-13 ~ 09-06, 카카오 T 몫 0.77, 실측 날씨): **446,712건**, 56일 모두 실측 날씨 연결.
  일별 (생성 − 기대)/√기대 = 평균 0.17, 표준편차 1.04 → 포아송 생성과 일치 (`notebooks/01_EDA_and_Spatial.ipynb`).
- 같은 설정 두 번 실행(각각 새 프로세스, 1시간, rl_prepositioned): 수요 지문·대기시간까지 동일 (`module4_dispatch/experiments/check_determinism.py`).

## 4. 이 데이터로 다시 학습한 결과
| 항목 | 예전(가정 수요, H3 res 7, 셀 3개, 8일) | 1차 실측 보정(전체 실측량, 2022 시간대) | **지금**(카카오 몫 0.77, 2025 시간대, 실측 날씨) |
|---|---|---|---|
| demand_v2 (t+1~t+6, 10분) WAPE | 44.6% | 23.0% | **26.4%** |
| RMSE / MAE | 2.91 / 1.91 | 3.22 / 1.99 | 2.84 / 1.78 |
| 포아송 잡음 하한 WAPE | — | — | 24.8% |
| 나이브 / 지난주 같은 칸 / 1시간 평균 | — | — | 36.2% / 36.8% / 30.5% |

WAPE가 23.0% → 26.4%로 오른 것은 모델이 나빠져서가 아니다. 카카오 몫만 쓰면서 칸당 호출이 평균 6.7건으로 줄어,
진짜 기대값을 알아도 남는 무작위 오차(포아송 하한)가 24.8%로 올라갔다. 모델은 그 하한과 1.6%p 차이다.

H3 해상도 비교(실측 보정 14일, 10분 칸, 노트북 01): res 7은 셀 3개에 한 칸이 86%(너무 거칠다),
res 9는 0인 칸 47%·자기상관 0.13, res 10은 0인 칸 65%(너무 잘다) → **res 8**(셀 8개, 0인 칸 30%, 한 칸 최대 46%, 자기상관 0.27).

## 5. 한계
- TIMS는 월 합계라 시간대 분포는 서울 전체 2025년 비율, 요일 안 배율은 2022년 1월 비율을 쓴다. 강남역 특유의 심야 집중은 덜 반영된다.
- 칸 안의 도로별 배분은 POI 가정이다(실측 아님).
- 영역 밖 이동을 경계 도로 하차로 단순화했다. 기본은 "같은 수의 빈 택시가 들어온다"는 가정이고, 반대 극단으로
  `taxi_external_away`(밖으로 나간 택시 중 강남구 하차/승차 비율 0.918만큼만 대체, 나머지는 운행시간 2배 뒤 복귀)를 민감도로 함께 본다.
- 카카오 T 몫 0.77은 서로 다른 해의 조사(앱 호출 비중 2024, 점유율 2022)를 곱한 근사다. 전체 실측량 기준 결과는 `full_demand` 시나리오로 함께 낸다.
- 날씨 효과(강수 1mm당 +1.99%)는 강남구 출발 생활이동(택시만이 아닌 전체 이동, 2026-08 22일)으로 추정한 계수다. 택시만의 비 오는 날 반응은 따로 검증하지 못했다.
